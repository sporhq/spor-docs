# Contributing

This repository is the source for [docs.sporhq.io](https://docs.sporhq.io),
the documentation for [Spor](https://github.com/sporhq/spor). It is an
[Astro Starlight](https://starlight.astro.build) site; pages are Markdown/MDX
under `src/content/docs/`. Fixes and additions are welcome — a typo fix and a
new reference page go through the same PR flow.

## Local setup

You need Node 24 (the version CI builds with). Then:

```sh
npm install
npm run dev      # live preview at localhost:4321
npm run build    # static build into dist/
```

Run the build before opening a PR — it catches broken frontmatter and dead
internal links that the dev server tolerates.

## Where pages live

Each sidebar section is one directory under `src/content/docs/`:

| Directory               | Section                                                        |
| ----------------------- | -------------------------------------------------------------- |
| `start-here/`           | Installation, quickstarts, connecting an assistant, core ideas |
| `use-spor/`             | The everyday loop — capture, the queue, briefings, dispatch    |
| `hosted/`               | The hosted product — organizations, sign-in, tokens, export    |
| `reference/cli/`        | CLI reference, one entry per `spor` verb                       |
| `reference/mcp/`        | The MCP surface — the operating loop, tools, embedded views    |
| `reference/api/`        | The versioned HTTP API — endpoints, authentication, errors     |
| `reference/graph-model/`| The graph model — nodes, edges, schemas, claims, lenses        |
| `contributing/`         | This guide and the style guide                                 |

A few loose reference pages (`reference/configuration.md`,
`reference/costs-and-controls.md`, `reference/diagnostics.md`) sit directly
under `reference/`.

Filenames are kebab-case (`personal-access-tokens.md`) and become the URL
slug. Most sections' sidebars are autogenerated from their directory, so a
new page appears once its frontmatter is in place. The one exception is the
Reference section, whose group structure is assembled in `astro.config.mjs`
— a new page directly under `reference/` also needs an entry there. Moving
or renaming a page changes its URL; add a redirect from the old path in
`astro.config.mjs` when you do.

## Page frontmatter

Every page opens with Starlight frontmatter:

```yaml
---
title: Personal access tokens
description: Mint, use, and revoke tokens for the CLI and the API.
sidebar:
  order: 3
---
```

`title` and `description` are required; the description is one plain sentence,
shown in search results and link previews. `sidebar.order` sets the page's
position within its section — check the neighboring pages' orders and pick a
number that slots yours where it belongs.

## Adding a reference entry

Reference sections (CLI, API, MCP) document one thing per entry: a verb, an
endpoint, a tool. Match the shape of the neighboring entries in that section —
same heading levels, same order of parts — so the section reads as one page
repeated, not many styles mixed.

Reference pages describe shipped behavior, and every entry should be verified
against its source of truth before it is written down:

- for the client surface and the graph model, the public client package
  [`@sporhq/spor`](https://github.com/sporhq/spor) — its README and API docs;
- for CLI entries, the CLI's own help output: `spor help` and
  `spor <verb> --help`. If the docs and the help output disagree, the help
  output wins;
- for API and MCP entries, the observed behavior of a server you can access —
  the actual response, not the response you expect.

If you find a page that contradicts shipped behavior, either fix it (citing
what the tool actually prints or returns in the PR description) or file a
[documentation error issue](.github/ISSUE_TEMPLATE/docs-error.md).

## The two CI checks

Besides the build, CI runs two repo-specific checks on every PR. Both run
locally, and running them before you push saves a round trip.

### Boundary lint

```sh
scripts/check-boundary.sh
```

The public docs describe the Spor server abstractly. Four categories of terms
are banned from every tracked file: private repository names and paths, server
deployment internals, server-side configuration variables, and real
identifiers from any team's graph (node ids, person handles, organization
names). The machine-readable list is `scripts/boundary-denylist.txt`.

Client-side surface is fine to document — environment variables the CLI reads,
token formats, the public API. The line is what runs on the server side and
what belongs to a real team's data.

When the lint fails it prints the offending file and line. The fix is to
rewrite the passage abstractly ("the server", "the hosting infrastructure") or
to replace a real identifier with a fictional one — see the
[style guide](https://docs.sporhq.io/contributing/style-guide/) for example-data rules. Do
not edit the denylist or the lint script in a docs PR; those are maintained
separately.

### Design-token parity

```sh
scripts/check-token-parity.sh
```

`src/styles/tokens.css` is a byte-identical vendored copy of the canonical
Spor design tokens, and it is never edited in a docs PR — token changes come
from upstream maintainers, who re-sync the copy with `scripts/sync-tokens.sh`.
If this check fails on your branch, the almost certain cause is a stray edit
to `tokens.css`; revert it. Site-specific styling belongs in
`src/styles/theme.css`, which maps the tokens onto Starlight's variables.

## Style

Prose follows the [style guide](https://docs.sporhq.io/contributing/style-guide/): the Spor
voice, the terminology glossary with canonical casing, example-data rules, and
formatting conventions. Read it before writing more than a sentence or two —
consistent terminology is most of what makes a reference usable.
